# Locator stability and locator pages

- Status: accepted
- Date: 2026-09-28

A plan for the next two capabilities of [Tested elements](../apps/docs/features/tested-elements.md). **Track A** shows
which tested elements are reached through brittle locators, with a replacement checked on the live page. **Track B**
records the page each locator is used on, so the overlay shows what tests do on the page in front of you, and warns
when a locator a test uses there no longer finds its element. The tracks are independent; Track A ships without a
wire or schema change.

**Status.** Proposed 2026-09-26. Steps 1 to 6 built on 2026-09-27, in one pull request. Open question 2, the
path-prefix mapping, built on 2026-09-28 as `pathPrefix` and `testPathPrefix` on project URL patterns and local
mappings; the other three open questions are still open. Track A is core, extension and dashboard work. Track B adds a
capture-fixture attachment, one payload column on `test_runs_cases` and two `locator_usages` columns, and adds
contracts that freeze at 1.0 (a new D19 in [`1.0-stabilization.md`](../proposals/1.0-stabilization.md)).

**Summary.** Tested elements answers "which tests reach this element?". These two tracks make it answer "which of
those locators will break?", which serves two of the four aims in [`ROADMAP.md`](../ROADMAP.md): hand back a fix,
and find what your tests miss. Track A judges every chain of the locator index with a few named rules
(position, CSS classes and structure, XPath, generated ids, long copy, numbers from data) as stable, watch or brittle.
The judge is one pure function in `@piwitests/core`, shared by the extension and the dashboard. When a brittle chain
finds exactly one element on the live page, the overlay builds a replacement from that element. It keeps the
replacement only if the same rules call it stable and the Playwright-faithful engine finds only that element with it,
and it chooses among the survivors with the same ladder locator healing uses. Track B records, in the capture fixtures, the page each
locator call ran on: the call site, the chain as Playwright prints it, and a normalized page key. Ingest joins that to
the index. The overlay then defaults to what tests do on the current page, and lists the locators tests use there that
now find nothing, or find several elements where a click needs one. That works before the suite runs, on any
deployment you can open in a browser.

- Track A alone gives the **At risk** tab with its **Brittle** section, a mark on boxes reached by a brittle chain,
  the findings and the replacement in each element's card, and a stability filter on the dashboard's Locators page.
- Track B adds the **This page / All pages** switch, the **Missing here** and **Several match here** sections, the
  pages of each use in cards and on the Locators page, and a page filter there.

## What exists

- **The locator index.** `locator_usages` holds one row per (test, Playwright project, branch, call site, action,
  chain), built from the stored steps (`apps/application/server/utils/locator-usages.ts`). It is served whole as a
  `LocatorIndex` (`packages/core/src/locator-index.ts`), with tests referenced by position.
- **The overlay.** `coverage-scan.ts` evaluates every chain with the in-page engine (`locator-engine.ts`, checked
  against real Playwright by `locator-engine.spec.ts`) and folds the matches per element. `coverage-panel.ts` draws the
  summary and three tabs, and `coverage-layer.ts` draws the boxes and cards. The `__piwiCoverage` bridge is what the
  e2e suite reads.
- **Ranking and judging.**
  - `generateAlternatives` (`packages/core/src/locator-generation.ts`) scores the candidates for an element, from 100
    for a test id down to 10 for a hashed class.
  - `classifyCssStability` and `isAutoGenerated` already judge single classes and ids.
  - Healing's `recommendLocatorFix` (`apps/application/shared/locator-healing.ts`) keeps the failing locator's method
    family when an alternative in it scores at least 50.
  - The overlay already derives a top locator for untested elements (`top-locator.ts`).
- **What nothing judges yet** is a chain a test uses. The lint overlay (`lint-scan.ts`) judges elements, not chains.
- **What nothing records** is the page a chain ran on. The Tested elements page lists this as the first thing the
  overlay cannot tell.
- **The capture fixtures see the page at every call.** `wrapLocator` (`capture-fixtures.ts`) wraps every locator a
  page creates and runs at each action and assertion, with the page and the call site (`captureCallerLocation`) in
  hand. `Locator.toString()` prints the chain in the index's own format; checked on Playwright 1.63:
  `locator('.btn-primary').nth(2)`, `getByTestId('x').filter({ hasText: /pay/i }).first()`. The page windows
  `recordPageWindow` cuts exist only with the opt-in page inventory, and attribute by time.
- **Page keys.** The Test Map normalizes page URLs with `pageNodeKey` (`shared/graph.ts`, over `normalizeRoute` in
  `shared/utils/route.ts`): path only; numeric ids, UUIDs, ULIDs, JWTs and long tokens collapsed to placeholders; no
  query, no hash.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | One pure function in core judges a chain from its text. The extension and the dashboard call it; nothing is stored. | The index already carries the chains to both. A rule change then ships with no migration and no re-index. |
| D2 | Three levels: stable, watch, brittle. A chain takes the level of its worst call. Only brittle is listed. | A stable container cannot save a brittle target, and a brittle container breaks every chain inside it. A watch finding is worth a line on a card, not a list entry. |
| D3 | A replacement is offered only for a chain that finds exactly one element here. The same rules must call the replacement stable, and the engine must find only that element with it. | A suggestion Piwi's own rules would flag, or one that finds a different element, is worse than none. |
| D4 | The replacement is picked with healing's ladder (`recommendLocatorFix`), moved to core. | One policy for "which fix" in healing and in the overlay. The test keeps its style when that style is stable. |
| D5 | One **At risk** tab with a section per kind, most urgent first: missing here, several match here, brittle. | The panel is narrow and already has three tabs. The three kinds answer one question, which locators will break, at three horizons. |
| D6 | A locator's page is recorded where the call happens: in the capture fixtures, at the start of each action and assertion, keyed by (call site, chain). | It is exact, with no inference from time windows or `goto` steps. It needs the fixtures; without them a use has no page and the overlay behaves as it does today. |
| D7 | Only a normalized page key and the page's origin leave the machine. The Test Map's normalization moves to core as `pageKey`. | No query, no hash, and no raw ids or tokens are sent. The keys equal the Test Map's page keys, so the two can be joined later. |
| D8 | No new reporter option: page recording rides locator capture (`captureLocators`, `PIWI_CAPTURE_LOCATORS`). | It runs in the same wrapper, and the page URL already travels in page state and network requests. Every new option is 1.0 surface (see the reporter configuration decision in the stabilization list). |
| D9 | Pages are stored per execution as a content-addressed payload, then indexed into `locator_usages` with `page` in the unique key and an `arrival` flag beside it. | A rebuild has to keep pages, and the payload rule forbids fat inline columns. Putting `page` in the key reuses upsert and purge unchanged, as `branch` did. |
| D10 | "On arrival" means no locator interaction happened on the page since its last main-frame navigation. | It separates "the page should show this as soon as it loads" from "the test opened something first", which is the main source of false alarms. |
| D11 | **This page** is the default once the index has pages. A use with no page counts as here. | This removes the false matches the docs list first, and hides nothing from runs that recorded no page. |
| D12 | Missing here needs an interaction or a positive assertion. Several match here needs an interaction. | Negative and count assertions expect absence or several elements, and some assertions take a list. An interaction is always strict. |
| D13 | Third-party pages keep their origin in the key. | A payment or sign-in provider's `/login` must never match the app's own `/login`. |

## Track A — Brittle locators

### A1. The rules

`packages/core/src/locator-stability.ts` exports `LOCATOR_STABILITY_RULES` (id, level, one-line reason) and
`assessLocatorChain(chain)`, which returns `{ level, findings: [{ rule, level, call, reason }] }`. CSS and XPath are
read by a small tokenizer, not a selector engine: classes, ids, attributes, pseudo-classes and combinators. The parts
of a Playwright `>>` selector are judged one by one.

| Rule | Level | Catches | Example |
|---|---|---|---|
| `position` | brittle for `nth(n)` with n ≥ 1; watch for `first()`, `last()`, `nth(0)` | picking an element by its order | `getByRole('listitem').nth(2)` |
| `css-class` | brittle when `classifyCssStability` rates the class 25 or less (utility, hashed, CSS-in-JS); watch for a semantic class | styling hooks | `locator('.bg-blue-500')`, `locator('.css-1q2w3e')` |
| `css-structure` | brittle | child and sibling combinators, `:nth-child()`, `:nth-of-type()`, `:first-child`, `:last-child`, three or more compound selectors deep, a descendant chain made only of tags (`div span`) | `locator('form > div:nth-child(2) input')` |
| `xpath` | brittle when absolute or indexed; watch otherwise | XPath | `locator('//main/div[2]//button')` |
| `generated-id` | brittle | ids `isAutoGenerated` recognizes | `locator('#radix-:r4:')` |
| `style-attribute` | brittle | `[style…]`, `[class=…]` | `locator('[style*="display: block"]')` |
| `long-text` | watch | an exact string over 40 characters in `getByText`, a `name` or `hasText` | marketing copy |
| `data-text` | watch | a number inside an exact string: a count, a price, a date | `getByRole('button', { name: 'Cart (3)' })` |
| `deep-chain` | watch | more than three locating calls | four chained `getBy…` calls |

Not flagged: `getByTestId`; `getByRole` with a name; `getByLabel`, `getByPlaceholder`, `getByAltText`, `getByTitle`;
an `#id` that is not generated; `[name=…]` and `[data-testid=…]`; a single tag inside a container
(`getByTestId('search').locator('input')`); a regex, which already says which part matters; a short text. A tag or an
unnamed role that matches several elements is not a stability problem: the overlay already shows it as ambiguous, and
Track B lists it under Several match here when a test clicks it.

### A2. The replacement

1. Offered only for a chain at brittle level (or watch, on the card) that resolves to exactly one element here. That
   element is then the one the test means.
2. Probe the element (`probeElementAttrs`) and rank candidates with `generateAlternatives`. Keep the ones
   `assessLocatorChain` rates stable, then the ones the engine resolves to exactly that element here.
3. Pick with `recommendLocatorFix(the brittle chain's target method, candidates)`. That tries the same method, then
   the same family, then the most stable. When the most stable candidate differs from the pick, show it too: healing's
   recommended and durable pair.
4. With no candidate left, say "No stable locator for it: give it a test id", like healing's `suggestAddTestId`.

`recommendLocatorFix`, `LOCATOR_FAMILY` and `CONVENTION_STABILITY_FLOOR` move to core and
`apps/application/shared/locator-healing.ts` re-exports them. The extension then runs the healing ladder itself, not
a copy.

### A3. In the overlay

- **At risk**, a fourth tab. Track A fills its **Brittle** section, and Track B adds two sections above it.
  - One row per brittle chain, under the element it finds.
  - Each row shows the findings as words (`position · CSS class`), the tests, and the call sites. Rows used by flaky
    or failing tests come first, because a brittle locator is a likely suspect in those tests.
  - Each row carries the replacement, with **Copy locator** and **Copy edit**. Copy edit copies each call site with
    the old and the new chain.
- **Boxes.** An element a brittle chain reaches gets an amber corner mark. A footer toggle, **Brittle**, shows or
  hides the marks, with a legend entry.
- **Card.** Under each chain: its findings, and the replacement with "finds only this element here".
- **Summary.** The meter line adds "N tested elements are reached through brittle locators".
- **Pick results.** A brittle chain in the reach groups shows its findings. The pick's own ranked list already offers
  the stable locator.
- **Bridge.** `__piwiCoverage.brittle` lists `{ description, locator, findings, suggestion, durable }` for the e2e
  suite.
- **Cost.** Chains are judged once per index, cached like the parsed chains. Replacements are built lazily and capped
  at 60, like the untested rows' suggestions.

### A4. On the dashboard

- **The Locators page.** Each chain's muted line says "Brittle: position, CSS class" or "Watch: long text". A filter
  (All, Brittle, Watch) sits in the URL as `?stability=`, beside `?q=`. **Who uses this?** shows the findings.
- It runs client-side with the same function, so it works in the demo.
- There is no replacement on the dashboard, because it has no live element. See Not in this plan.

### A5. Docs and tests

- Docs:
  - A **Brittle locators** section in `tested-elements.md` (the page uses under 1,000 of its 1,500 words).
  - A new `reference/locator-stability.md` with one row per rule id, checked against `LOCATOR_STABILITY_RULES` by the
    docs drift test, as `reference/clues.md` is.
  - The term "brittle locator" in `guide/concepts.md`. "Fragile" is taken: it names a Test Map gap class.
  - A paragraph on the Locators page in `locator-usage.md`.
- Tests:
  - Core: one table-driven case per rule, plus the stable forms that must never be flagged.
  - Extension e2e: the shop fixture gains brittle chains (`locator('.btn-primary').nth(1)`,
    `locator('#input-1748291')`, `locator('//main/div[2]//button')`, `getByText('Only 3 left in stock')`). Assert the

  - Dashboard e2e: the stability filter.

## Track B — The page of each locator use

### B1. Capture

- **Recording.** In `wrapLocator`, record at the start of every action, and of every `expect` on a wrapped locator
  (every expression, negations included, before the pass-through):
  `{ location: captureCallerLocation(), locator: String(target), origin, page: pageKey(page.url()), arrival }`.
  `page.url()` is synchronous and local; it makes no protocol call.
- **Arrival.** Each page keeps a counter of locator interactions (the actions `isInteractionAction` names). A
  main-frame `framenavigated`, which fires for full loads and same-document navigations alike, resets it to 0. A call
  is on arrival when the counter is 0 when it starts.
- **Limits.** Entries are deduped by (location, chain, page), with arrival OR-ed across duplicates. At most 1,000
  entries per test, and chains of at most 1,000 bytes (the index's own limit). `about:`, `data:` and `blob:` pages are
  skipped.
- **Transport.** Attached as `piwi-locator-pages` at teardown, whatever the outcome. The reporter parses it in
  `onTestEnd`, as it parses `piwi-locators`, into `locatorPages`, and `toWireTestCase` projects that onto
  `WireTestCase`.
- **Packaging.**
  - One exported helper, `internal/capture/locator-pages.ts`, that the dogfood `apps/application/tests/fixtures.ts`
    calls rather than re-inlining.
  - `normalizeRoute` and `pageNodeKey` move to `packages/core/src/page-key.ts` (as `pageKey`).
    `shared/utils/route.ts` and `shared/graph.ts` re-export them, so the Test Map's keys do not change.

### B2. Storage and the index

- **Wire.** `locatorPages` on `TestCasePayload` and `StreamEventPayload` (`shared/types.ts`) and on `WireTestCase`,
  with the leaf shape `LocatorPageUse` in `@piwitests/core/wire`, pinned by `wire-shared-drift.test.ts`.
- **Per execution.** `test_runs_cases.locator_pages_payload_id` points at a content-addressed payload, with an
  index. The shared persist path writes it for both server and demo. Both reference lists in `retention.ts` (the
  candidate collection and the `NOT EXISTS` guard) name the new column, or the payloads would be collected.
- **Sanitizing** (`server/utils/locator-pages.ts`, shared by server and demo):
  - The chain is canonicalized (parse, then render); one that cannot be read is dropped.
  - The location is made project-relative with the root the steps use.
  - The page key is normalized again.
  - An own-origin page (the run's `baseURL`s plus the project's route origins, as in the Test Map) keeps its path key.
    Any other page's key becomes `origin + path` (D13).
- **Index rows.**
  - `locator_usages` gains `page` (`''` when unknown, in the unique key) and `arrival`.
  - `buildLocatorUsageRows` joins each step use to the execution's pages by (call site, chain), and falls back to
    (`file:line`, chain) when the columns differ. A use with pages emits one row per page; one without emits one row
    with `''`.
  - The key-byte budget counts the page; a key over 300 bytes is stored as `''`.
  - Upsert and purge are unchanged apart from the key, and `arrival` follows the newest run.
- **Rebuild.** The rebuild reads the payload next to the steps, so pages survive it.
- **Index response.**
  - `LocatorIndex.pages` lists the page keys, most used first. Each use gets `pages` and `arrival` as positions into
    that list.
  - All three are optional: an older extension ignores them, and a newer one reads their absence as "page unknown".
  - A use on more than 50 pages lists 50 and sets `pagesTruncated`. The overlay then counts it on every page, but
    warns only on the pages listed.
- **Other responses.** `LocatorUsageSite.pages` and `ExecutionLocatorUse.pages` carry the same information for
  **Who uses this?** and for an execution's Locators tab.

### B3. In the overlay: this page

- **Current page.** The current key is `pageKey(location.href)`, read at every scan. An SPA route change mutates the
  DOM, which already triggers a rescan. The key is shown in the panel's subtitle.
- **The switch.** **This page** / **All pages**. This page is the default once the index has any page.
  - A chain counts here when one of its uses was recorded on this key, or has no page.
  - All pages is today's view.
- **Elements tested elsewhere.** In This page, an element reached only through chains used on other pages is not
  tested here. Its Not tested row says which locator matches it and where tests use it: "matches
  `getByRole('button', { name: 'Save' })`, used on /settings".
- **Card.** The pinned card lists the pages of each use and marks the ones on arrival.
- **Link.** **Find these locators in Piwi ↗** passes the page, so the Locators page opens filtered to it.

### B4. In the overlay: missing and several here

Both sections appear in This page only, above Brittle.

- **Missing here.** A chain with a use on this page whose actions need the element: an interaction, or a positive
  assertion. `expect.not.*`, `toBeHidden`, `toHaveCount` and `count` never count. The chain resolves to nothing now.
  - On-arrival rows come first: "tests find it as soon as this page loads". The rest follow: "tests reach it after
    acting on the page: open the menu or dialog first".
  - Each row shows the chain, the action, the tests, the call sites and the Playwright projects, so a mobile-only use
    on a desktop window is visible as such. A brittle chain in the list shows its findings, because a brittle
    locator that finds nothing is the likeliest cause.
- **Several match here.** A chain with an interaction on this page that resolves to more than one element. A chain
  ending in `first()`, `last()` or `nth()` resolves to one by construction.
- **Live, and a hint.** Both sections update as the page changes. The wording is "finds nothing here now", never
  "broken".
- **The pre-flight.** Open a preview deployment of a branch, and select the default branch in the panel. Missing here
  then lists what the default branch's tests will not find on the branch's UI, before its suite runs.
- **Pill.** When Missing here has on-arrival rows, the collapsed pill says so.

### B5. On the dashboard

- **The Locators page.** Each chain says "Used on /checkout, /cart and 3 more", and a page filter sits in the URL as
  `?page=`.
- **Other views.** **Who uses this?** shows the pages of each call site. An execution's Locators tab shows the page
  of each use.
- **Demo.**
  - Seed pages payloads for the seeded executions; the backfill at database open builds the pages.
  - The simulator emits `locatorPages`.
  - Re-seed and commit `seed.version.json`.

### B6. Docs and contracts

- `tested-elements.md` covers This page / All pages, Missing here and Several match here. "What it does not tell you"
  loses its first point for projects with the capture fixtures. The Needs chips stay as they are; Setting it up says
  the fixtures add pages.
- `locator-usage.md` covers pages in the index and what they need. `guide/capture-fixtures.md` says what the fixtures
  record. `guide/concepts.md` defines "page key".
- `1.0-stabilization.md` gets **D19**, the new contracts:
  - the `piwi-locator-pages` attachment shape;
  - the `locatorPages` wire field;
  - the index fields `LocatorIndex.pages`, and `LocatorIndexUse.pages`, `.arrival` and `.pagesTruncated`.
- `apps/application/ARCHITECTURE.md` (the locator index), `apps/extension/ARCHITECTURE.md` (Tested elements) and the
  reporter's attachment list in `packages/reporter/ARCHITECTURE.md` describe the new pieces.

## Risks

- **Rules that flag too much.**
  - Two levels, with only brittle listed, contain it.
  - Before PR 2 ships, run the judge over the dogfood and demo indexes and count findings per rule. A rule that flags
    more than a third of a well-kept suite's chains drops to watch.
- **A replacement right for this state of the page only.** It is checked against the page as it is now, and the card
  says so.
- **Join misses.** The wrapper's stack and Playwright's step location could disagree on the column. The join falls
  back to `file:line`, with unit tests on real stacks, and PR 4's integration test checks the join on a real run.
- **Older Playwright.** The recorded chain is canonicalized by parsing it. If a version prints a chain the parser
  cannot read, that use gets no page and behaves as it does today; nothing breaks.
- **Index size.** Pages add one list plus two small arrays per use. Measure it on the dogfood project against the
  extension's cache; an index over the quota already comes back uncached.
- **False alarms in Missing here** from data, sign-in state, feature flags or viewport. These mitigations limit them:
  - arrival ranking;
  - the projects shown on each row;
  - the "now" wording;
  - the pill only counts on-arrival rows.
- **New 1.0 contracts.** D19 lands with PRs 4 and 5.

## Open questions

1. **Hash routers** (`/#/checkout`). The key drops the hash, as the Test Map's does, so every such route is `/`.
   Recommendation: leave it until someone needs it, since changing it changes the Test Map's keys too.
2. **A deployment under a path prefix** (`/app/checkout` while the tests ran at `/checkout`). **Built** 2026-09-28:
   an optional `pathPrefix` on a project URL pattern (`project_url_patterns.path_prefix`, the Settings tab, the
   endpoints) and on a local mapping, edited in the extension's settings. The extension removes it, whole segments
   only, before comparing the page with the index (This page, Missing here, Several match here, the pick results), and
   before keying a bug report's page; the overlay's subtitle and notes name the prefix removed. The reverse case, tests
   that ran under a prefix the site does not use, is `testPathPrefix` (`test_path_prefix`), put in front of the page's
   path after `pathPrefix` is removed, so the two together swap one prefix for the other.
3. **Viewport and Playwright project.** Should Missing here keep only the projects that match the window, desktop or
   mobile? Recommendation: show the projects on each row first, and add a filter if the rows prove noisy.
4. **Page-level actions** (`page.keyboard`, `page.mouse`, `page.click(selector)`) do not reset or count toward
   arrival. Recommendation: leave them out at first, so arrival means "no locator interaction since the page loaded".

## Not in this plan

- Replacements on the dashboard from healing's stored alternatives (`locator_snapshots.alternatives`, per call
  site), so a brittle chain gets a fix without the page open.
- An MCP tool that hands an agent the brittle chains with their call sites and pages.
- Test Map `reaches` edges from test to page built from locator pages. They would be exact, where today's come from
  the end-of-test page and the opt-in inventory.
- A count of brittle locators as an analytics metric.

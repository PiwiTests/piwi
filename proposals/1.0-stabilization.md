# 1.0 stabilization — the decision list

ROADMAP's Next section holds one item: settle the wire format and API surface, then commit to semver stability. A
full audit of the HTTP surface (160 routes), the reporter↔server wire contract, the 40-tool MCP registry and the CLI
produced two kinds of findings: inconsistencies cheap to fix immediately (shipped in #398/#400 — summarized at the
bottom), and **decisions** — places where 1.0 freezes whatever is chosen, so choosing has to happen first. This
document is the durable home for those decisions; the numbers below are stable references. When a decision ships,
move its entry to "Settled" with the PR number.

Every claim was verified against `main` after #398, #399 and #400 merged.

## Open decisions

### D4. Wire versioning and the compatibility policy

There is no wire-format version anywhere in the reporter↔server exchange: `reporterVersion` is stored but never
branched on, unknown fields are silently ignored, missing fields silently default, and the reporter's only
compatibility mechanism is the any-error fallback ladder (streaming → upload → submit). Nothing pins reporter
*bytes* to server *handlers* — the drift test pins the declared types, which the ingest handlers do not use.
**Recommendation, as a package:** (a) write the policy down — "the server accepts payloads from any ≥1.0 reporter;
unknown fields are ignored" — in the OpenAPI description and `upgrading.md`, including which side to upgrade first;
(b) add a `wireVersion` field the server echoes and can someday reject with a distinguishable status; (c) have the
reporter preflight `GET /api/version` (unauthenticated, already exists) and log when a feature will degrade;
(d) add a golden-payload fixture test replaying canned 1.0 `submit`/`events`/`finish` bodies against the real ingest
routes, so "old reporters keep working" is CI-checked rather than hoped.

### D12. Reporter configuration surface

Env names diverge from option names in ways that freeze at 1.0: `inspectOnFailure` → `PIWI_INSPECT_ON_FAIL`,
`pickLocatorOnFailure` → `PIWI_PICK_LOCATOR_ON_FAIL`, `ai.mode` → `PIWI_AI`, `ai.maxSteps` →
`PIWI_AI_MAX_FLOW_STEPS`; `PIWI_AI_UPDATE` lives outside the `PIWI_ENV_KEYS` single-source map. The master switch
`collectPerformanceMetrics` has no env var while its three sub-toggles do. Docs drift: `reporter.md` claims every
option has an env var (false for ten), documents a `serverUrl` default that does not exist, and the npm README's
options table is roughly ten options behind with no drift test covering it. **Recommendation:** add the missing
env var and register `PIWI_AI_UPDATE`; either rename the divergent vars now with old names as aliases or bless them
in the docs as-is; regenerate the README table (or point it at the docs site) and fix the two false claims.

### D13. CLI flag semantics

`--project` means the Piwi project in `piwi init` but the *Playwright* project in `piwi ai resolve`; `--dir` means
the skills directory in `piwi skills add` but the AI-artifacts directory in `piwi ai check` while `init` calls the
former `--skills-dir`. Flag names are frozen contract for CI scripts at 1.0. Also `ci.md`'s table gloss of
`--require-tag` omits that a tag matching no test is itself a violation. **Recommendation:** rename
`ai resolve --project` → `--pw-project` (keeping the old flag as a hidden alias) and align `--dir` naming; fix the
doc gloss.

### D15. Write the informal contracts down

Not changes — documentation debts that become contract at 1.0: the multipart field-name mix (camelCase alongside
`trace_<i>`/`report_<type>`/`attach_meta_<i>`, plus the legacy `htmlReport` field still accepted); the `type:
'complete'` discriminant sent in batch payloads but undeclared in `TestCasePayload`; and the split time encoding
(run-level `startTime` ISO-8601 vs case/attempt/step `startedAt` epoch-ms) which is fine but stated nowhere.
**Recommendation:** declare all three in the wire types/OpenAPI as-is; drop `htmlReport` only if no external
producer used it.

### D18. Test Map external contracts (M2)

The Test Map (M2) adds three external contracts that freeze at 1.0: the **`piwi-page-inventory`** capture attachment
(`[{ url, controls: [{ role, name }], links: [{ name, href }] }]`, a `pageInventory` wire field on the per-case
payload); the **probe plan and results** exchange (`GET /probes/plan` → `{ budget, items: [{ testCaseId, testTitle,
routeKey, fault, nth }] }` and `POST /probes/results`), where the `fault` vocabulary (`status-500`, `empty-body`,
`drop-field`, `stale-value`, `slow`) is the frozen surface; and the **`X-Piwi-Probe`** request header the
instrumentation reads (base64 JSON `{ nonce, ts, specJson, sig }`, HMAC-SHA256 over `${nonce}.${ts}.${specJson}`),
shared by the Nitro and ASP.NET Core packages. **Recommendation:** declare the attachment and probe payloads in the
wire types/OpenAPI as-is; the probe header format is documented in each instrumentation README and versions with the
`v` field in the envelope if it ever changes.

### D17. Test Map external contracts (M3)

M3 adds more external contracts that freeze at 1.0, on top of the M2 ones in D18:

- The **declared-surface manifest** shape (`shared/types.ts` `AppManifest`): `{ routes: [{ method, pattern,
  handler?, responses? }], pages: [{ pattern, name? }] }`, uploaded through **`PUT /api/projects/:id/surface/manifest`**
  with body `{ source: 'instrumentation' | 'committed' | 'openapi', manifest: AppManifest }` and read through
  **`GET /api/projects/:id/surface/manifest`**. The committed file is **`piwi.manifest.json`** next to the Playwright
  config; the instrumentation packages serve the same route table (minus documented codes) at **`/__piwi/manifest`**
  (`{ routes: [{ method, pattern, handler? }] }`), fetched by the reporter's global setup only when the base URL's
  first response carries an instrumentation header.
- The **`X-Piwi-Probe` header at level two** (server probes): the same base64 `{ nonce, ts, specJson, sig }` envelope
  as D18, but `specJson`'s `fault` vocabulary widens to the server fault classes (`throw`, `status`, `delay`,
  `dependency`, `data`, `extreme`, `replay`, `auth`, `slow-first`), and the instrumentation answers with
  **`X-Piwi-Trace`** reporting the fault it actually applied so an un-honored probe is recorded as inconclusive.
- The **feature-graph endpoint** **`GET /api/projects/:id/graph`** (`?node=kind:key&depth=`, depth capped at six) and
  the `get_feature_graph` MCP tool: the neighborhood shape (nodes with their class, edges with their kind, and the
  tests on each hop) is the frozen surface.

**Recommendation:** declare the manifest shape and the surface/graph endpoints in the OpenAPI as-is; the manifest and
probe-header formats are versioned by the `v` field in their envelopes (probe) or an additive field (manifest) if they
ever change.

### D19. Locator pages

The page each locator call ran on ([`locator-stability-and-pages.md`](../adr/locator-stability-and-pages.md), Track B) adds
three external contracts that freeze at 1.0:

- The **`piwi-locator-pages`** capture attachment and the **`locatorPages`** per-case wire field:
  `[{ location, locator, origin, page, arrival }]` (`LocatorPageUse` in `@piwitests/core/wire`), where `location` is
  the call site as a step location reports it, `locator` the chain as `Locator.toString()` prints it, `page` the page
  key (`pageKey` in `@piwitests/core/page-key`: the path with ids and tokens collapsed, no query, no hash) and
  `arrival` whether no locator interaction ran on the page since its last navigation.
- The **page key normalization** itself: the extension computes the key of the page it is on with the same function,
  so a change to it has to reach the reporter, the server and the extension together.
- The locator index document's optional **`pages`**, and each use's **`pages`**, **`arrival`** and
  **`pagesTruncated`** (`GET /api/projects/:id/locator-index`), which the browser extension reads.

**Recommendation:** declare the attachment, the wire field and the index fields as they are; they are additive and
optional, so an older reporter, server or extension simply has no pages.

### D20. Steps files and `piwi codegen`

A recording as data ([`bug-report-to-failing-test.md`](../adr/bug-report-to-failing-test.md), Part 1) adds two external
contracts that freeze at 1.0:

- The **steps file** (`PiwiSteps` in `@piwitests/core/steps`, version `v: 1`): `{ v, title, origin, recordedAt, note,
  steps }`, each step `{ action, target, value, redacted, pageUrl, timestamp, assertion? }` with URLs on `origin`
  stored as paths, and the limits `parseSteps` enforces. Piwi Picker writes it (Download steps), `piwi codegen` reads
  it, and a tester's file must still read on a developer's newer tools. Documented in
  `apps/docs/reference/steps-format.md`.
- The **`piwi codegen`** command and its flags (`--out`, `--force`, `--body`, `--title`, `--test-import`,
  `--absolute-urls`, `--no-url-checks`, `--env-values`, `--fail`, `--fail-reason`, `--tag`, `--project`,
  `--server-url`, `--api-key`, `--offline`) and exit codes (0 written or printed, 2 unreadable steps or a failed
  write), part of D13's CLI surface.

The `hover` action joined `v: 1` before 1.0 shipped (Piwi Picker records the hover that reveals what a click lands
on); an older reader rejects a file holding one as an unknown action rather than misreading it, and no 1.0 reader
exists yet.

**Recommendation:** freeze `v: 1` as it is, with new fields added as optional ones and a new version only for a
change an older reader would misread; keep reading the pre-format recording shape (`{ steps, startedAt, startUrl }`)
through 1.0.

### D21. Extension connect and project URL patterns

Connecting Piwi Picker in one step and keeping its URL patterns on the instance
([`extension-connect.md`](../adr/extension-connect.md)) adds external contracts that freeze at 1.0, since a published
extension talks to instances of any later version:

- The **device-code endpoints**: `POST /api/extension/connect` (`{ browser?, os? }` →
  `{ deviceCode, userCode, verificationUrl, interval, expiresIn }`), `POST /api/extension/connect/token`
  (`{ deviceCode }` → `{ status }` with `pending`, `slow_down` + `interval`, `denied`, `expired`, or `approved` +
  `apiKey` + `user`), and the page `/extension/connect?code=` the extension opens.
- **`GET /api/extension/url-patterns`**: `{ user, items: [{ projectId, projectName, projectLabel, pattern,
  environment, branch, pathPrefix, testPathPrefix }], projects: [{ id, label, canEdit }] }`, and
  `POST /api/projects/:id/url-patterns` (`{ pattern, environment?, branch?, pathPrefix?, testPathPrefix? }`), which the
  extension calls. Each prefix is null or a plain path (`/app`: a leading slash, no trailing one, no query, hash or
  wildcard, at most four segments). Before comparing a page with the tests' page keys, the extension removes
  `pathPrefix` from its path, whole segments only, then puts `testPathPrefix` in front; a path outside a set
  `pathPrefix` is left as it is. An extension older than a field ignores it; an instance older than it sends none,
  which reads as no prefix.
- The **pattern syntax**: `urlMatches` in `@piwitests/core/function-match` (`*` within a path segment, `**` across,
  anchored at both ends).

**Recommendation:** freeze them as they ship. New fields are optional additions; a new `status` value would break an
older extension's polling loop, so the set stays closed.

### D22. Bug reports

Bug reports as failing tests ([`bug-report-to-failing-test.md`](../adr/bug-report-to-failing-test.md), Parts 3 and 4) add
external contracts that freeze at 1.0:

- The **`expectedStatus`** wire field on every test case (Playwright's `TestCase.expectedStatus`, one of `passed`,
  `failed`, `timedOut`, `skipped`, `interrupted`), and the outcome read from it: a row stored `failed` whose expected
  status is `failed` is an expected failure that passed. A payload without it is read from the `fail`, `skip` and
  `fixme` annotations.
- The **`piwi:bug`** annotation (a bug report id, digits, an optional leading `#`), beside `piwi:link`.
- The **`bug.looks_fixed`** notification event and its payload (`{ projectId, projectName, runId, branch?, tests:
  [{ title, filePath, executionId, testCaseId, bugId?, link? }] }`).
- The **endpoints** Piwi Picker and the CLI call: `POST /api/projects/:id/bug-reports` (multipart: a `report` part,
  the bug report `{ v: 1, steps, evidence, context }` read by `parseBugReport` in `@piwitests/core/bug-report`, whose
  `context.pathPrefix` and `context.testPathPrefix` (optional) name the URL pattern's path prefixes removed from and
  added to `context.pageKey`, an
  optional `language` part, up to three PNG `screenshot` parts named as `evidence.screenshots` names them; or a JSON
  body `{ report, language? }`; answers `201 { id, url }`), `GET /api/projects/:id/bug-reports` (`{ items }`, `status`
  filter), `GET /api/bug-reports/:id`, `PATCH /api/bug-reports/:id` (`{ title?, status? }`),
  `POST /api/bug-reports/:id/reproductions` (`{ verdict, source?, divergedAt?, origin?, userAgent?, runId? }`),
  `GET /api/bug-reports/:id/spec?mode=commit|run` (`{ code, fileName, path, warnings, mode }`) and
  `GET /api/bug-reports/:id/screenshots/:index`. The statuses (`open`, `test-committed`, `looks-fixed`, `closed`,
  `dismissed`) and verdicts (`reproduced`, `not-reproduced`, `diverged`) are a closed set an older extension reads.
- The **CLI**: `piwi bug <id>` (`--write`, `--out`, `--no-run`, `--force`, `--run-mode`, `--server-url`, `--api-key`;
  exit codes 0, 1 the run did not fail as `test.fail()` expects, 2) and `piwi codegen bug:<id>`, part of D13's surface.
- The **MCP tools** `list_bug_reports`, `get_bug_report` and `render_steps`.
- Filing in a tracker: the `createIssue` part of the send (`true`), its `issue` answer (`{ status, key?, url?, error? }`
  or null), `GET /api/projects/:id/bug-reports/intake` (`{ tracker, projectKey, locale, canCreate, fileEvery }`), and
  `bug_report` as an `entityType` of `POST /api/integrations/issues`, `GET /api/integrations/issue-draft`, the links
  endpoints and the MCP tool `create_issue`.
- Why the suite missed it: `GET /api/bug-reports/:id/missed-by` (`{ page, pagesKnown, visiting, targets, mainFile,
  summary, owner }`), the `missedBy` field of `get_bug_report`, and `escaped-defect` blind spots keyed `page:<pageKey>`.
- The **desktop repro request** Piwi Picker sends to the desktop app: `POST /api/desktop/repro-requests` (JSON only,
  415 otherwise; `{ steps, options?: { headed, trace, project, repeatEach }, title?, bugReportId?, instanceUrl? }`, the
  steps read by `parseSteps`; answers `201 { id, status, expiresAt, windowOpen }`), `GET /api/desktop/repro-requests/:id`
  (`status` one of `waiting`, `running`, `done`, `declined`, `expired`; `verdict` one of `reproduced { step, found }`,
  `not-reproduced`, `diverged { step, reason }`, `completed`, `stopped`), the shell command `desktop_run_repro`
  (`{ projectId, requestId, args }`, flags only) and the `PIWI_REPRO_RESULT` file the spec writes (`{ status, line,
  message }`).
- **Pairing Piwi Picker with the desktop app**, the two routes the desktop guard leaves open:
  `POST /api/desktop/picker-pairings` (an extension `Origin` only, 403 otherwise; JSON only, 415 otherwise;
  `{ browser?, os? }`; three waiting at most, 429; answers `201 { id, secret, code, interval, expiresIn, windowOpen }`)
  and `GET /api/desktop/picker-pairings/:id` with `x-pairing-secret` (`status` one of `waiting`, `denied`, `expired`,
  `claimed`, and once `allowed` with `token`), and the `picker-pairing` message of the desktop event stream.

**Recommendation:** freeze them as they ship; new payload fields are optional additions.

### D23. Viewports in the locator index

Open this page at a viewport ([`devtools-panel.md`](../adr/devtools-panel.md), 2.5) adds one external contract that freezes
at 1.0: the locator index document's optional **`viewports`**, `[{ project, width, height }]`
(`LocatorIndexViewport` in `@piwitests/core/locator-index`, `GET /api/projects/:id/locator-index`), which the browser
extension reads. It is read from the run metadata the reporter already sends (`htmlReport.projects[].use.viewport`,
with the project's `name`), so no reporter wire field is added; that metadata field becomes part of the contract too.

**Recommendation:** declare the field as it is; it is additive and optional, so an older server simply has no
viewports and the extension offers a size typed by hand.

### D24. Flake Lab

[Flake Lab](../adr/flake-lab.md) adds its external contracts as it ships, one PR at a time. PR 1 adds one:

- The optional **`failure`** field on a captured network request: the `piwi-network` attachment entry and the
  `networkRequests` items of the per-case wire payload (`WireNetworkRequest` in `@piwitests/core/wire`, which also
  names the request's other fields for the first time). The capture fixtures record a request that failed without a
  response (Playwright's `requestfailed`) with `status: 0` and `failure` set to Playwright's error text
  (`net::ERR_CONNECTION_RESET`, `net::ERR_ABORTED`); a request that finished carries no `failure`. The server stores
  it in `network_requests.failure`.

PR 2 (suspects) adds:

- **`GET /api/test-cases/:id/flake-profile`**: `{ testCaseId, windowDays, maxAttempts, attempts, failures, passes,
  from, to, suspects, context }`. Each suspect is `{ id, kind, label, sentence, counts: { failuresWith, failures,
  passesWith, passes }, lift, condition, conditionLabel, executionIds }` plus, by kind, `route`, `thresholdMs`,
  `thresholdCount`, `testCaseId`, `title`, `project`, `sharedRoutes` and `approximate`; `kind` is one of `slow-route`,
  `failed-route`, `alongside`, `before`, `load`, `project`, and `condition` one of `delay { route, ms }`,
  `fail { route, status }`, `fail { route, abort }`, `cpu { rate }`, `alongside { testCaseId, title }`,
  `after { testCaseId, title }`, `project { name }` — the vocabulary the flake plan's conditions will use. A context
  item is `{ kind: 'attempt' | 'hour' | 'concurrent-run', label, counts, lift }`. A route key is the method and the
  `normalizeRoute` pattern without the query (`GET /api/cart/:id`).
- **`GET /api/projects/:id/flake-suspects?testCaseIds=`**: `{ items: [{ testCaseId, failures, passes, suspect }] }`,
  the top suspect of each listed test, for the flaky list.
- The MCP tool **`get_flake_profile { testCaseId }`**: the suspects and context above, with `experiments: []` until
  the lab stores any.
- The clue id **`known-flake-suspect`** (weak).
- The capability id **`flake-lab`** (module `workflow`, passive data), which a decision can decline.

PR 3 (flake mode) adds:

- The **flake plan file** (`FlakePlan`, parsed by `parseFlakePlan` in `@piwitests/core/flake-plan`), one per arm:
  `{ version: 1, experimentId, test: { file, title, suite, project }, arm: { id, conditions }, errorSignatures }`.
  `file` is project-root-relative with POSIX separators, `suite` the describe titles from the outermost down (empty
  matches any), `project` a Playwright project name or null, `experimentId` and `arm.id` strings, and
  `errorSignatures` the `flakeErrorSignature` of each of the test's failures in history. A condition is one of
  `delay { route, ms, match }`, `fail { route, status, match }`, `fail { route, abort: true, match }`, `cpu { rate }`,
  `network { latencyMs, downKbps, upKbps }`, `alongside { test: { file, title, suite } }`,
  `after { test: { file, title, suite } }` and `project { name }`; `route` is a route key (method and `normalizeRoute`
  path, `GET /api/cart/:id`, matched with `requestRouteKey` from `@piwitests/core/page-key`), and `match` is `all`
  (the default) or a 1-based ordinal counted after the page's first navigation. A plan with another `version` or an
  unknown condition kind is refused, never run with the condition dropped. The profile's `alongside`/`after`
  conditions name a test case id; the plan names the test by file, title and suite.
- The **error signature** a lab compares, `flakeErrorSignature`: `extractErrorSignature(text).normalizedMessage`
  (`@piwitests/core/error-signature`), the masked message head. Changing its masking changes which lab failures
  match history.
- The variables **`PIWI_FLAKE_PLAN`** (the plan file; a non-empty value switches flake mode on) and
  **`PIWI_FLAKE_RESULTS`** (the results file). Setting `PIWI_PROBE` and `PIWI_FLAKE_PLAN` together stops the run.
  Flake mode forces `retries` to 0.
- The **results line** (`FlakeResultLine`), one JSON object per line, appended per finished attempt of the target
  test and of an `alongside`/`after` companion: `{ version: 1, experimentId, armId, role: 'target' | 'companion',
  file, title, project, browserName, status, errorSignature, matchesHistory, startedAt, duration, workerIndex,
  parallelIndex, repeatEachIndex, retry, conditions }`. `status` is Playwright's (`passed`, `failed`, `timedOut`,
  `skipped`, `interrupted`), `errorSignature` is null unless the attempt failed, `startedAt` is epoch milliseconds
  and `duration` milliseconds (the span of the capture fixture around the test), and `conditions` holds one
  `{ kind, outcome, note? }` per plan condition on a target line (`outcome`: `applied`, `not-matched`, `skipped`,
  `by-command`) and none on a companion line.
- The run stamp **`piwiFlakeLab: { experimentId, armId }`** in the run's metadata. The server keeps a run carrying it
  out of every analysis a probe run is kept out of, and out of quarantine streaks and regression baselines.
- The verdict arithmetic in `@piwitests/core/flake-verdict`: a one-sided Fisher exact test on matching failures,
  **reproduced** at a rate of at least 0.5 with p < 0.05, **amplified** at p < 0.05 below it, **not reproduced**
  otherwise, and `N = max(5, ⌈ln 0.05 / ln(1 − rate)⌉)` clean runs to verify a fix.

PR 4 (the CLI and experiments) adds:

- **`piwi flake <test>`** and **`piwi flake verify <test>`** (part of D13's CLI surface): `<test>` is a test case id
  or `file:line`; the flags `--suspect <n>`, `--all`, `--runs <n>`, `--budget <duration>`, `--no-upload`,
  `--plan <file>`, `--json`, `--server-url`, `--api-key`, `--project` (the Piwi project, for `file:line`); and the
  exit codes 0 (reproduced; `verify`: the fix held), 1 (not reproduced; `verify`: still fails or too few runs), 2
  (error). The connection order is the one `preflight` uses. Each arm runs as `playwright test <files> --grep <tests>
  --repeat-each=<n> --retries=0 --workers=<1|2> [--project=<name>]` in batches of up to 5 repeats, and counts the
  target's attempts in start order, cut after the 3rd matching failure (`FLAKE_BATCH_RUNS`,
  `estimateFlakeSessionMs` in `@piwitests/core/flake-plan`). The `--json` document is `FlakeReport` in
  `packages/reporter/src/cli/flake.ts`.
- **`GET /api/test-cases/:id/flake-plan`** (`?kind=reproduce|verify&runs=&commit=&source=cli|desktop|ci&machine=&record=`):
  `{ version: 1, experimentId, kind, projectId, testCaseId, test, displayTitle, windowDays, failures, passes,
  failureCommit, medianDurationMs, errorSignatures, suspects, control, arms, combined, verifies }`. An arm is
  `{ id, label, suspectId, rank, conditions, runs, stopAt }` with the conditions in the plan-file shape; `id` is
  `control`, `suspect-<rank>`, `combined` or `verify`. It records an unfinished experiment unless `record=false`;
  roles administrator and reporter; 409 for `verify` when nothing reproduced the test.
- **`POST /api/projects/:id/flake-lab/results`**: `{ experimentId, commit?, playwrightProject?, arms: [{ id, label?,
  suspectId?, conditions, runs, matchingFailures, otherFailures, discardedRounds?, stoppedEarly? }] }`, answering
  `{ experimentId, kind, verdict, arms: [{ id, verdict, pValue, rate }] }`. The server computes every verdict from the
  counts; the control arm is required, and the `verify` arm for a verify experiment. Roles administrator and
  reporter; 409 for an experiment that already has results.
- **`GET /api/test-cases/:id/flake-experiments`**: `{ items }`, finished experiments newest first, each `{ id,
  testCaseId, kind, verdict, commit, failureCommit, source, machine, playwrightProject, createdAt, finishedAt,
  reproducingArmId, verifies, arms }`. Reproduce verdicts are `reproduced`, `amplified`, `not-reproduced`; verify
  verdicts `verified`, `still-fails`, `inconclusive`.

### D27. Ingest health

`metadata.ingestHealth` on a run records what ingest left out or rebuilt, so the run page and the AI context can say
a step or console line is absent because it was dropped. It joins the run metadata that `GET /api/test-runs/:id`
returns. Every field is optional and the key is absent on a run stored whole:

- **`stepsDropped`**, **`consoleEntriesDropped`**: steps and console entries the ingest caps left out
  (`PIWI_INGEST_MAX_STEPS`, `PIWI_INGEST_MAX_CONSOLE_ENTRIES`), summed over the run's executions.
- **`tracesSkipped`**: traces sent with the run that the server did not store.
- **`evidenceFromTrace`**: executions whose console, network or ARIA evidence was rebuilt from their trace.
- **`submitFallback`** (`{ path, reason? }`): written by the reporter in the run metadata it sends. `path` is one of
  `upload` (the multipart upload instead of finishing the live stream), `submit` (the JSON submit instead of the
  multipart upload) and `recovery` (the copy saved locally when every submit failed, sent by a later run); `reason`
  one of `results-lost`, `finish-failed`, `upload-failed`.

The server keeps only `submitFallback` from the metadata a reporter sends; the counts are its own, and a later
metadata write (`/begin`, `/finish`) keeps them.

**Recommendation:** freeze the key and its fields as they ship; a new count or fallback path is an optional addition,
and the enums are closed sets.

### D28. The `run.interrupted` event

The stale-run sweep marks a run `interrupted` when its reporter goes quiet. It now sends a **`run.interrupted`**
notification with the run payload every `run.*` event carries (`RunFinishedPayload`, `status: "interrupted"`), so the
subscription filters on branch, environment, status and owners apply to it. Lab runs send none. The finish-time side
effects (regression signals, markers, AI diagnosis, the other run events, PR feedback, auto-heal) do not run, since a
later event carrying the run's stream token revives it. The event name joins the notification registry
(`NOTIFICATION_EVENTS`) that webhooks and subscriptions name, which freezes at 1.0.

**Recommendation:** freeze the name. A run revived and then finished sends its `run.finished` as usual; a run
interrupted twice sends one `run.interrupted`, as the outbox deduplicates per run and channel.

### D29. Run origin

Every run records what launched it, and the dashboard decides from it which analyses the run may feed (one rule,
`shared/run-eligibility.ts`). Three names join the wire that freezes at 1.0:

- **`PIWI_ORIGIN`**, read by the reporter from the Playwright process's environment: one of `ci`, `ci-rerun`,
  `local`, `desktop`, `editor`, `preflight`, `bug`, `flake-lab`, `probe`, `bisect`, `reproduce`. Unset, the run is
  `ci` when a CI provider is detected and `local` otherwise; an unknown value is ignored with a warning. `import` is
  the server's own, for imported reports.
- **`PIWI_ORIGIN_REF`**, optional: what the run was launched for (a dispatch, a cluster or a bug report id), letters,
  digits and `._:/#@-`, at most 200 characters; anything else is dropped.
- **`metadata.piwiOrigin = { kind, ref? }`** on the run, additive on the wire. The server keeps it only when `kind` is
  known and rebuilds it with `kind` first. Runs stored before it read as `probe` or `flake-lab` from their lab stamps,
  `import` from `metadata.import`, `ci` from `metadata.ci`, and `local` otherwise.

The launchers that set it: the desktop app (`desktop`; `reproduce` and `bisect` with the cluster id; a Piwi Picker
reproduction as `reproduce` with the bug report id), the editor service (an `env` field on `piwi/runArgs`,
`piwi/runSelection` and `piwi.runCommand`, which both clients apply), `piwi preflight --run`, `piwi bug --write` (with
the report id), Flake Lab (with the experiment id) and probes.

**Recommendation:** freeze the variable names, the shape and the kinds as they ship; a new kind is an addition that
older servers drop, so a launcher that needs one checks the server version first.

### D30. CI re-run correlation

A CI re-run from a cluster's page records a dispatch id, the branch it ran on, the spec files and, when the provider
answers with one, GitLab's pipeline id or Bitbucket's build number (`lastRerunDispatch` on the cluster). When a CI run
finishes, it is matched to an open dispatch by its `PIWI_ORIGIN_REF`, the pipeline id or the build number, and on
GitHub, which returns no run id, by branch, a start within six hours and exactly the dispatched spec files. A matched
run's origin becomes `ci-rerun` with the dispatch id as its ref. The project setting
**`ciRerun.github.dispatchIdInput`** (optional) names the `workflow_dispatch` input that receives the dispatch id;
GitHub rejects an undeclared input, so it is sent only when set, and the workflow passes it on as
`PIWI_ORIGIN_REF`.

**Recommendation:** freeze the setting name and the dispatch record's added fields (`id`, `ref`, `files`,
`pipelineId`, `buildNumber`, `runId`) as optional; the six-hour window and the file rule stay implementation details.

### D31. Environment incidents on the run and the wire

A finished run whose failures come from the environment under test (the app's host refusing connections, a name that
does not resolve, a crashing browser) is flagged by the server and left out of every analysis that compares runs.
Four names join the surface that freezes at 1.0:

- **`metadata.incident = { rule, reason, host, projects, failedTests, executedTests, hostFailures, decidedBy, by?,
  decidedAt, firstRunId }`** on the run, written by the server only (`sanitizeMetadata` drops it from a reporter's
  metadata, and finalizing again keeps the stored one). `rule` is one of `host-unreachable`, `browser-crash`,
  `cross-project`, `person`; `decidedBy` is `rule` or `person`; `projects` holds the ids of the other projects where
  the same host or error failed within 30 minutes; `firstRunId` is the first flagged run of the same outage.
- **`metadata.incidentReview = { decision, by, at }`**, `decision` one of `marked`, `cleared`: a person's decision,
  which the classifier never overrides.
- **`environment.incident`**, a notification event: `{ runId, projectId, projectName, status, totalTests,
  failedTests, branch?, environment?, isDefaultBranch?, rule, reason, host?, otherProjects, incidentKey }`. It replaces
  the run's `run.failed`, `run.failed.default_branch`, `flakiness.spike`, `perf.regression`, `cluster.new` and
  `bug.looks_fixed` (`run.finished` still fires), is not delivered to a subscription filtered on owners, and is
  deduplicated per channel on `incidentKey`, so one outage across projects is one message.
- **`POST /api/test-runs/:id/incident`** (`{ incident, reason? }` → `{ runId, incident, review }`), any role that may
  edit the run.

**Recommendation:** freeze the key names, the `rule`, `decidedBy` and `decision` sets, and the event's payload as they
ship; the thresholds (80% of tests failed, 70% of failures reaching the host, 50% with another project, 30 minutes)
are implementation details that may be tuned, and a new rule is an addition older readers show by its id.

### D32. The gate's inconclusive verdict

`POST /api/test-runs/:id/gate` adds **`verdict`**, one of `passed`, `failed`, `inconclusive`, to its result, and
**`facts.incident = { rule, reason, host }`** when the run is an environment incident. An inconclusive result has
`passed: false` and no violations, so a client reading only `passed` blocks the merge. `piwi gate` exits **`3`** for
it, beside `0` satisfied, `1` violated and `2` could not evaluate.

**Recommendation:** freeze `verdict`, its three values and exit code `3`. An older server sends no `verdict`; the CLI
then reads `passed` as before.

### D33. Hand-back outcomes

What happened to each thing Piwi hands back is stored as rows of `handback_outcomes` (`shared/handback-outcomes.ts`
holds the value sets; `recordOutcome` in `server/utils/outcomes.ts` is the one write path, idempotent on the kind, the
subject, the suggestion key, the outcome and the run). The MCP tools and the metrics will expose three closed sets:

- **Kinds:** `locator-heal`, `auto-heal-pr`, `diagnosis`, `fix-attempt`, `gap-draft`, `bug-spec`,
  `quarantine-proposal`, `merge-suggestion`, `gate`, `flake-verify`.
- **Outcomes:** `suggested`, `applied`, `verified`, `rejected`, `regressed`.
- **Channels:** `inferred` (read from the runs, no actor), `ui`, `mcp`, `editor`, `desktop`, `cli`, `ci`.

A row's subject is one of `test-case`, `cluster`, `gap`, `bug-report`, `heal-action`, with an optional suggestion key
naming what was suggested (a heal's call site and locators, a diagnosis version, a merge's cluster pair, a heal PR's
dedupe key). An `applied` locator heal read from the runs carries the label `matched-recommendation`: it says the code
that ran uses the recommended locator, not who wrote it. Rows follow `PIWI_RETENTION_DAYS`; before they are pruned
they are counted into `handback_outcome_rollups` per project, UTC day, kind, outcome and channel.

**Recommendation:** freeze the three sets as they ship; a new kind, outcome, channel or subject type is an addition
that readers must tolerate. The suggestion key's format stays an implementation detail.

### D35. Bisect results

A first bad commit is recorded on a failure cluster by any instance, not only the desktop app: the desktop app for a
bisect it ran against itself, an editor for one the desktop app ran for a team instance's failure, an agent over MCP.
Two names join the wire that freezes at 1.0:

- **The body of `POST /api/failure-clusters/:id/bisect`** (`BisectResultBody` in `@piwitests/core/bisect`):
  `{ sha, subject?, author?, date? }`, `sha` 7 to 40 hex characters (lower-cased), the others trimmed and at most 500
  characters, `date` an ISO date. 400 without a valid SHA; reporter or administrator; answers
  `{ ok, bisectedCommit: { sha, subject, author, date, commitUrl } }`. The fix plan reads it as `bisectedCommit`.
- **`set_cluster_bisect`** (`{ clusterId, sha, subject?, author?, date? }` → `{ clusterId, sha, subject?, author?,
  date? }`), the MCP tool over the same handler (`recordClusterBisect`) with the same role check, like D26's.

`GET /api/projects/:id/latest-run` takes an optional `origin` and `ref`: the newest run stamped with that run origin
(D29), so the desktop app links a local run to the run its reporter recorded.

**Recommendation:** freeze the body and the tool's arguments as they ship; new fields are optional additions.

### D36. Desktop jobs from the editor

An editor passes a job on a team instance's failure to the desktop app on the same machine, through the app's
repro-request endpoints, with the token from the app's discovery file (`~/.piwi/desktop.json`). The window shows the
job and runs nothing until the developer starts it there; the editor polls the verdict and shares it on the team
instance with its own key. What joins the wire that freezes at 1.0:

- **The job request** (`DesktopJobRequest` in `@piwitests/core/desktop-job`), the body of
  `POST /api/desktop/repro-requests` beside Piwi Picker's steps: `{ kind, commit, good?, tests, browser?, title?,
  instanceUrl, clusterId? }`. `kind` is `reproduce` or `bisect` (a request without `kind`, or `steps`, is Piwi
  Picker's); `commit` and `good` are 7 to 40 hex characters, `good` required for a bisect; `tests` is 1 to 50
  `{ filePath, title, line?, projectName? }` with `filePath` relative to the Playwright config (no leading `-`, `/`
  or drive, no `..`). Nothing in it is code or a command-line flag: the app builds the command.
- **The request view** (`GET /api/desktop/repro-requests/:id`) gains `kind`, `job` and `jobVerdict`: `reproduced`,
  `not-reproduced`, `first-bad` with `{ sha, subject, author, date }`, `error` with a `reason`, or `stopped`;
  `steps` is null for a job. The window records the verdict through `PATCH …/:id` (`jobVerdict`).
- **The editor protocol**: the request `piwi/desktopJob` (`{ root, executionId, kind }` → `{ ok, message, jobId? }`)
  that the client command `piwi.desktopJob` sends from the quick fixes, the notification `piwi/desktopJobChanged`
  (`{ jobId, kind, status, message, share }`, `status` one of `running`, `done`, `declined`, `expired`, `gone`) and
  the request `piwi/shareDesktopJob` (`{ jobId }` → `{ ok, message, url? }`).
- **The desktop app's run references**: every local run is stamped with a `PIWI_ORIGIN_REF` (D29): the cluster or
  bug report it was launched for, else `job:<request id>` for an editor's job, `repro:<request id>` for a Piwi Picker
  request without a report, and `desktop:<random>` for a plain local run. The Tauri commands that start a run take an
  optional `originRef`.

**Recommendation:** freeze the request, the verdict kinds and the protocol names as they ship; a new job kind is an
addition an older app refuses with 400, which the editor reports.

### D37. Flake Lab from the editor and the failure pages

A flaky test's Flake Lab step reaches the editor, the failure pages and Home, and can run in CI. What joins the wire:

- **`GET /api/projects/:id/flake-lab`**: each test gains `flakeRate` (the share of the runs read in which it failed at
  least once, null off the ranking); with **`suspects=true`**, the first tests that need a step also carry
  `suspect: { id, label, standing, matchingFailures, runs, lab } | null` and `untestedSuspects`. `standing` is one of
  `untested`, `reproduced`, `amplified`, `not-reproduced`; `lab` is display text, not a contract.
- **The flake plan** (`GET /api/test-cases/:id/flake-plan`, `plan_flake_experiment`): each suspect gains
  `lab: { verdict, matchingFailures, runs, note } | null`, and `arms` come in the order the lab runs them (untested
  suspects first, one that did not reproduce last) rather than by rank; an arm's `rank` stays its suspect's rank, so
  `--suspect <n>` is unchanged. `note` is display text.

### D39. Gate evaluations and the gate commit status

Each `POST /api/test-runs/:id/gate` is stored as a row of `gate_evaluations`: the run, its commit, the pull request
(the run's `metadata.scm.prNumber`, else the one its feedback was posted on), the policy and a hash of it, `passed`,
`verdict`, the violations, the clusters of the run's new regressions, and a `source`. The response is unchanged and
the run is not modified. What joins the surface:

- **The request header `X-Piwi-Client: cli`**, which `piwi gate` sends; `source` is `cli` with it and `api` without.
- **The project setting `gateStatus`** (`PATCH /api/projects/:id`, boolean, off by default): with it, and with
  pull-request feedback posting commit statuses, each verdict is posted as the commit status
  **`<statusContext>/gate`** (`success` when the policy passed, `failure` with the first violation when it failed).
  An inconclusive verdict posts nothing.
- **The `gate` hand-back outcomes** (D33) on the new subject type **`gate-evaluation`**: a failed verdict records
  `suggested`; a pull request merged while its last evaluation before the merge failed records `rejected` (an
  override); a cluster of that evaluation's new regressions failing again on an eligible default-branch run within 30
  days of the merge records `regressed` (an escape). Details carry `{ prNumber, verdict, rules }`, plus
  `{ clusterId, escapedRunId }` on an escape. The `gate:sweep` task reads pull-request states every ten minutes.

**Recommendation:** freeze the header value, the setting, the status context suffix and the subject type as they
ship. The policy hash's format, the escape window and the sweep's cadence stay implementation details.

### D40. The pull-request feedback record

**Recommendation:** no wire field reads it yet; freeze the columns when an endpoint or MCP tool first exposes the

### D41. Auto-heal outcomes on the wire

What auto-heal learns from its pull requests joins the wire in three places:

- **`healPr` on `cluster.fixed`**: `{ number, url, actionId }`, set when a commit among those since the cluster last
  failed carries a `Piwi-Heal: <dedupe key>` trailer naming an auto-heal action whose edits cover the cluster. It is
  optional, and `verification` keeps its two values whatever it says. The trailer's name and its value (the action's

**Recommendation:** freeze `healPr`'s three fields, the trailer name and the marker as they ship; new fields are

### D43. Agent diagnoses

### D44. Fix attempts and the `Piwi-Cluster` trailer

### D51. Flake Lab jobs from the editor

A third kind of desktop job (D36): the editor passes a flaky test's Flake Lab experiment from a team instance to the
desktop app, which runs it on the developer's machine, and the editor records the results on the team instance, where
the test's flake profile reads them. The same model holds: the window runs nothing before a click, and the app never
holds the team's key. What joins the wire:

- **The job `flake-lab`** on `POST /api/desktop/repro-requests` (`DesktopJobRequest` in `@piwitests/core/desktop-job`):
  `{ kind: 'flake-lab', commit, plan, title?, instanceUrl, clusterId? }`. `plan` (`FlakeLabJobPlan`) is the reproduce
  plan the editor read with its own key from `GET /api/test-cases/:id/flake-plan` with `kind=reproduce`,
  `source=desktop`, `machine=<host>` and `record=true`, kept to the fields `piwi flake --plan <file>` runs (`suspects`
  empty, `verifies` null); `commit` is its `failureCommit`. The app refuses a plan whose test paths are not relative to the Playwright config,
  whose project names break the Playwright-project pattern, whose arm ids do not match `^[a-z][\w-]{0,63}$`, or whose
  conditions the plan-file parser (`parseFlakePlan`) refuses: those values reach Playwright's command line.
- **The verdict `lab`**: `{ kind: 'lab', report: { verdict, reproducingArm, commit, arms } }`, `verdict` one of
  `reproduced`, `amplified`, `not-reproduced`, and `arms` the arms that ran, `{ id, runs, matchingFailures,

- **Sharing**: `piwi/shareDesktopJob` on a `flake-lab` job posts `POST /api/projects/:id/flake-lab/results` to the
  experiment the plan recorded, each arm's label and conditions from the editor's copy of the plan, its counts from the
  report; the instance computes the verdicts as it does for the command line.
- **The editor protocol**: `DesktopJobKind` gains `flake-lab`; `DesktopJobParams` is `{ root, executionId?,
  testCaseId?, kind }`, `testCaseId` naming the test of a `flake-lab` job; a summary line's command may be
  `piwi.desktopJob`, which a flaky test's line carries. A failure whose test's Flake Lab entry has `untestedSuspects`
  (or a top suspect `untested`) offers the job as a quick fix.
- **The desktop app**: the Tauri command `desktop_flake_lab_job({ projectId, requestId })`, which reads the request
  from the app's own server, and a `lab` event on `piwi:local-run` carrying the report it printed.

**Recommendation:** freeze the kind, the plan's fields, the `lab` report and the parameters as they ship; new fields are
optional additions, and an older app refuses the kind with 400, which the editor reports as too old.

### D52. The base-URL check

**`checkBaseUrl`** (reporter option, `PIWI_CHECK_BASE_URL`, default `false`): the reporter's global setup checks,
before it registers the run and before any worker starts, that each `baseURL` used by the projects `--project`
selects answers, through Playwright's request context with the project's `ignoreHTTPSErrors` and `proxy`. Any HTTP
answer counts except a `502`, `503` or `504`. When one does not answer after three tries, the setup throws a message
that starts `[Piwi Dashboard] The app under test did not answer` and names each base URL, its projects and the
error; Playwright stops with its failure exit code, no test runs and no run reaches the dashboard. A reporter whose
run never began (its global setup threw, a spec did not load) uploads nothing and saves nothing for recovery.

**Recommendation:** freeze the option name, its environment variable, its default and what counts as an answer. The
number of tries, their timeout and the message wording may change. Recording the stopped run on the dashboard as an
incident would be an addition, a new wire field.

### D58. The assistant

The in-app assistant ([`in-app-assistant.md`](../adr/in-app-assistant.md)) answers questions with the AI model, reading
through the MCP read tools with the asking user's access. What joins the wire:

- **`GET /api/assistant/status`** (`{ available, reason, provider, model, toolMode }`, `reason` one of
  `not-configured`, `declined`; `toolMode` one of `native`, `json-action`, or null until known).
- **Conversations**, each private to its owner (another user's id is a 404, administrators included):
  `GET /api/assistant/conversations` (`{ items: [{ id, title, createdAt, updatedAt }] }`, at most 50),
  `POST /api/assistant/conversations` (`{ title? }` → the summary, 201), `GET /api/assistant/conversations/:id` (the
  summary plus `messages[]`: `{ id, role, blocks, context, toolCalls, provider, model, inputTokens, outputTokens,
  status, error, createdAt }`, `role` one of `user`, `assistant`, `status` one of `completed`, `failed`, a tool call
  `{ name, arguments, summary, error?, entities? }`) and `DELETE …/:id` (`{ success }`). Every route is `signed-in`,
  and 403 while the capability is declined.
- **A message's `blocks`**, in the order they were written (`AssistantBlock` in `shared/assistant.ts`): `text`
  (`{ text }`, Markdown, an entity link written `[label](piwi:<type>/<id>)`), and the blocks the server checked before
  sending: `code` (`{ id, language, code, title? }`), `command` (`{ id, command: { bash, powershell? }, title? }`),
  `patch` (`{ id, patch, validation, title? }`, `validation` null without SCM), `entity` (`{ id, entity, status?,
  detail? }`), `options` (`{ id, prompt, options[], picked? }`), `question` (`{ id, prompt, multiple, choices[], other,
  answer? }`, `answer` `{ choiceIds, other? }`), `checklist` (`{ id, title, steps[] }`, a step `{ id, text, command?,
  guide?, done? }`), `guide` (`{ id, guide: { title, stops[] } }`, a stop `{ anchor, route?, title, body }`),
  `navigate` (`{ id, route, label }`) and `proposal` (`{ id, action, title, change, target, projectId, params,
  outcome? }`: a change the user applies with a click, `action` one of the closed list in `shared/assistant-actions.ts`
  — `resolve-cluster`, `ignore-cluster`, `reopen-cluster`, `quarantine-test`, `release-test`, `diagnose-cluster`,
  `diagnose-execution`, `keep-run`, `decide-capability`, `decide-project-capability` — each calling an existing route
  from the browser with the user's session, `target` the entity or null for an instance-wide change, `outcome`
  `{ status, result?, at }` with `status` one of `applied`, `dismissed`, `failed`). An entity is `{ type, id, label }`,
  `type` one of `project`, `run`, `execution`, `cluster`, `test-case`.
- **`POST /api/assistant/conversations/:id/messages`** (`{ text, context?, reply? }`, `context` `{ route, page?,
  params?, query?, projectId?, anchors? }`, `anchors` the guide anchor ids rendered on the page, at most 300 of at most
  60 characters, `reply` `{ messageId, blockId, choiceIds, other? }` answering a `question` or
  `options` block of an earlier answer of the same conversation, recorded on the block as `answer` or `picked`),
  answered as Server-Sent Events: `text` (`{ text }`), `tool` (`{ name, summary, entities? }`, the entities its result
  named), `block` (`{ block }`, one block other than text, whole), then one `done` (`{ messageId, provider, model,
  toolMode, inputTokens, outputTokens, costUsd }`) or `error` (`{ code, message, messageId }`, `code` one of `limit`,
  `timeout`, `provider`, `invalid-reply`). A `question` or `options` block ends the answer. 503 with
  `AI_NOT_CONFIGURED`, 409 while the conversation answers another question, 404 for a `reply` to a message of another
  conversation, 400 for picks the block does not offer.
- **`PATCH /api/assistant/conversations/:id/messages/:messageId/checklist`** (`{ blockId, stepId, done }` →
  `{ block }`, the checklist as it now stands): ticks one step of a `checklist` block, for the conversation's owner
  only (404 otherwise, and for a message, block or step it does not hold).
- **`PATCH /api/assistant/conversations/:id/messages/:messageId/proposal`** (`{ blockId, status, result? }`, `status`
  one of `applied`, `dismissed`, `failed`, `result` at most 300 characters → `{ block }` with its `outcome`): records
  what became of a `proposal` block, for the conversation's owner only (404 otherwise, and for a message or block it
  does not hold; 409 for one already applied or dismissed). The change itself goes through the action's own route.
- **`POST /api/assistant/conversations/:id/mcp`**: the MCP endpoint (Streamable HTTP, JSON-RPC: `initialize`, `ping`,
  `tools/list`, `tools/call`) of one answer the Claude Code CLI writes, which the CLI the server starts calls the
  answer's tools on; a call that changes the tools offered answers as an event stream led by
  `notifications/tools/list_changed`. Authenticated only by the bearer token minted for that answer (`pwt_…`), 401
  without it, after the answer ends, for another conversation and from a host, origin or peer that is not loopback.
  The desktop app's guard lets this one route through on that token. `toolMode` `native` for the `claude-cli`
  provider when the installed CLI can run an answer this way.
- **Nudge dismissals**, each private to its owner as a conversation is (with authentication off, one list every
  visitor shares): `GET /api/assistant/nudge-dismissals` (`{ items: [{ nudgeId, dismissedAt }] }`, in the order they
  were dismissed), `PUT /api/assistant/nudge-dismissals/:nudgeId` (→ `{ nudgeId, dismissedAt }`; dismissing it again
  keeps the first date) and `DELETE …/:nudgeId` (`{ success }`, 404 when it was not dismissed). `nudgeId` is one of
  `undecided-capabilities`, `diagnosis-without-diff`, `failure-without-fixtures` (`ASSISTANT_NUDGE_IDS` in
  `shared/assistant-nudges.ts`), 400 otherwise. `signed-in`; they answer while the capability is declined, when the
  nudges that offer a guide still show.
- **The AI role `assistant`** (`PIWI_AI_ASSISTANT_*`, a `roles.assistant` in the AI settings), the diagnosis model
  when unset; the limits `PIWI_AI_ASSISTANT_MAX_TOOL_CALLS`, `…_MAX_OUTPUT_TOKENS`, `…_TURN_TIMEOUT_SECONDS`,
  `…_DAILY_TOKENS_PER_USER`, `…_DAILY_TOKENS` and the horizon `PIWI_ASSISTANT_RETENTION_DAYS`.
- **The capability `assistant`** (module `agents`, instance level, follows `ai`, declined over its data), and
  `assistantTurns` per model and in the totals of the AI usage summary.

**Recommendation:** freeze the routes, the event names and payloads, the conversation and message shapes, the block
kinds and their fields, the `piwi:<type>/<id>` link form and the error codes as they ship; new block kinds join the
`block` event's union additively, and new proposal actions join `action`'s list additively, each calling a route that
already exists; new nudge ids join `nudgeId`'s list additively. The tools each page is offered, the system prompt, the
block limits (`ASSISTANT_BLOCK_LIMITS`), the limits' defaults, the history a question carries, and which nudges a page
offers, their rules and the browser's weekly budget may change. The answer's MCP
endpoint is called only by the CLI this server starts: its token's form, the tools it lists and the turn limit the
CLI runs with may change.

## Settled (for reference)

Decided and shipped while the audit was fresh:

- **Query parsing (D10)** — a `requireIntQuery`/`optionalIntQuery`/`queryFlag` helper trio
  (`server/utils/query-params.ts`) gives every query-parsing route one **clamp-and-400** contract: present-but-invalid
  is a 400 (never a silent default, never a dropped filter), absent falls back to the declared default, integers clamp
  into `[min, max]`. Applied to the int params on `slow-tests`, `timeout-opportunities`, `flaky-tests`, `performance`,
  `ai-steps`, `spec-health`, `stability-trend`, `settings/ai/usage`, cluster `commits`, `projects/[id]` and `links`;
  the boolean flags on `performance` (`fullRunsOnly`), `quarantine` (`candidates`), execution `diagnosis-context`
  (`includeImages`) and the three diagnosis POSTs (`force`); and the `subscriptions` `projectId` filter that used to
  silently return everything on garbage input. The strictness ships before the freeze (flipping silent-default to 400
  is the breaking part, so it lands pre-1.0). Live-verified: garbage/float/bad-bool → 400, valid → 200, absent →
  default.
- **Error conventions (D8)** — the same failure class now answers with the same status across the surface.
  Uniqueness conflicts are **409** everywhere (projects, tags, users join test-functions, which already was); a
  missing notification channel is **404** everywhere (subscription create was 400, subscription patch was 403 — both
  now 404, matching channel test/delete). Validation failures stay **400** (present-but-invalid input, unchanged). The
  env-managed-conflict semantic is documented as one rule — *the environment is authoritative for the fields it owns* —
  expressed at the two natural granularities: `wasted-waits` owns the whole setting so a write is refused with **409**,
  while `settings/ai` owns only provider/key/baseUrl so those are ignored and model-only overrides still apply (both
  now say so in their OpenAPI). The soft-fail family — the three "test the destination" endpoints
  (`channels/[id]/test`, `settings/ai/test`, `settings/smtp/test`) that return **200 `{ success: false, error }`**
  when a reachable destination rejects the delivery — is documented in each route's OpenAPI `responses`,
  distinguishing the delivery outcome from request-level errors (which keep their 4xx/503).

  For the machine-readable code, the chosen mechanism is the **`data.errorCode` convention** (not a global error
  handler, which would have to reimplement Nuxt's whole error path). Every server route throws a new `apiError`
  helper (`server/utils/api-error.ts`) instead of `createError` — all 329 sites migrated — so the serialized `data`
  is **always** an object `{ errorCode, issues? }`, never the bare zod-issues array it used to be. `errorCode` is a
  stable string from a shared vocabulary (`shared/utils/error-codes.ts`): it defaults from the status (404 →
  `NOT_FOUND`, 409 → `CONFLICT`, a 400 carrying issues → `VALIDATION_ERROR`, …) and is overridden where a client
  needs to distinguish failures that share a status — the two "not configured" 503s become `AI_NOT_CONFIGURED` vs
  `SMTP_NOT_CONFIGURED`. The demo service worker emits the same shape from the same vocabulary. No consumer read the
  old nested `data`, so the shape change broke nothing; adding a code later is additive (unknown codes fall back to
  the status). Live-verified: dup → 409 `CONFLICT`, missing channel → 404 `NOT_FOUND`, invalid body → 400
  `VALIDATION_ERROR` + `issues`, other 400 → `BAD_REQUEST`.
- **Phantom shard fields (D3)** — run-level `shardIndex` was on the wire in every reporter body but nothing read it.
  Chosen: persist it. `test_runs` gains a nullable `shard_index` column (SQLite + Postgres migrations), and the
  streaming (`start`/`setup`) and `submit` ingest paths store the creating shard's index alongside `shardTotal` (null
  for non-sharded runs); the demo router mirrors it. The field stays in the payload types and OpenAPI, now backed by a
  column that's queryable for debugging shard merges.

- **Run-status spelling (D1)** — the British `initialising` is renamed to the American `initializing`, matching its
  sibling `finalizing`. A clean rename with no compatibility alias: the stored value, the `run-initializing` SSE event,
  the MCP `list_runs` vocabulary and the UI all move together, and the `TestRunStatus` union, the schema comments and
  the reporter/docs prose are updated to match.
- **List envelopes and pagination (D6)** — every list route now returns a single `{ items: [...] }` envelope so lists
  can grow metadata (totals, cursors) after 1.0 without a break; the test-case catalog's `{ items, total, limit,
  offset }` and MCP's `{ items, nextCursor }` were already compliant. Shipped endpoint by endpoint across seven
  batches (bare-array analytics, the content CRUD family, the settings/user CRUD, project analytics, flaky-tests +
  clusters, the project/run listings, and finally `GET /api/projects`), each keeping the app green: server route +
  demo router + UI + E2E moved together, the UI using a `useFetch`/`$fetch` `transform` (or a renamed named-response
  type) so downstream code stays array-shaped and TypeScript flags every consumer. The `commits` composite renamed
  its collection to `items` beside its metadata. Shared handlers and MCP tools kept their `{ <noun> }` shape (MCP is a
  separate surface). Pagination vocabulary settled too: `limit`/`offset` for row pagination, `runs`/`days`/`buckets`
  as documented domain windows (`performance`'s `limit`→`runs`). No compatibility aliases, per the "no backward
  compatibility" call.
- **Small route-level oddities (D16)** — the query parameters routes actually read are now declared in their OpenAPI:
  `force` on the three diagnosis POSTs (`test-run-cases/[id]/diagnose`, `failure-clusters/[id]/diagnose` and its
  `/stream`), `runs`/`from`/`to`/`fullRunsOnly` on project `performance`, `runs` on `slow-tests`,
  `baseline`/`branch`/`limit` on cluster `commits`, `sha` on `commit-diff`, `status` on `cluster-merge-suggestions`,
